# Почему сохраняются результаты аналогов

В опыте меняется только выбор первых 15 строк. Каждое расстояние вычисляется тем же выражением и сохраняется как исходный JavaScript Number. Данные, геометрия, признаки, назначение групп и число аналогов не меняются.

Для конечных расстояний исходный comparator задаёт полный порядок: сначала расстояние, затем индекс МО для `sixNeighbors` либо `id.localeCompare` для `nearest`. Собственное МО сохраняет расстояние `Infinity`, как в исходном коде. На реальном пакете 2016 территорий остальные расстояния конечны, поэтому собственное МО не попадает в первые 15. Для малого синтетического набора сохраняется прежний результат, даже если размер запроса включает все строки.

После обработки первых i строк массив `best` содержит первые `min(15, i)` строки их устойчивой сортировки. Это верно для пустого начала. Если новая строка не лучше последней из 15, она не может попасть в первые 15; при равенстве остаются ранее встретившиеся строки. Иначе двоичная вставка помещает её после уже встретившихся равных строк и перед большими. Последняя лишняя строка удаляется. Получаются первые 15 строк устойчивой сортировки первых i+1 строк, что завершает индукцию.

При NaN расстояния comparator может не задавать тот же полный порядок. Для этого случая helper выполняет исходный `sort().slice()`. Тот же путь оставлен для отсутствующего, отрицательного и нецелого `count`, чтобы сохранить правила `slice`. Целый нулевой `count` возвращает пустой список. Целый `count` больше числа строк возвращает все строки в том же порядке.

Индукция объясняет корректность выбора. Отдельная проверка `DeepEqual` сравнивает действующие функции, точные числа и порядок по всем МО и исключениям текущего пакета, а также на синтетических крайних случаях. Из доказательства не следует ускорение браузерной отрисовки: его проверяют другим опытом.
